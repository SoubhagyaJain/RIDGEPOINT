# Status

- Current phase: 3 complete, plus a Phase 3 follow-up on 2026-10-01 (not yet committed); wait for the user to say "continue" before Phase 4.
- Completed: Phase 2 V0 baseline and harness; Phase 3 owned BF16 Qwen2 forward pass, contiguous KV, static 10 ms/four-request batching, capacity preflight, preserved SSE API, numerical equivalence checks, real streamed V1 answer, and repeated same-trace comparisons.
- Measured V0 smoke: six fixed requests per trial at 0.3 offered req/s; 6/6 completions in each; goodput 0.25 req/s in all three trials. This is exploratory due small sample, Windows/WDDM, and absent continuous clock trace. See `results/summaries/phase2-v0.md`.
- Measured Phase 3 (original): all nine final runs completed 24/24 requests on one trace; V1 batches of up to four formed. V1 did not achieve a validated goodput gain: run-to-run timing varied sharply, most send-lag checks failed, and no continuous clock trace was captured. See `results/summaries/phase3-v1.md`.
- Measured Phase 3 follow-up: the original V1 decode step took about 1.5× the Hugging Face step in the same process because boolean-mask cache writes forced 113 host syncs per step; the fixed runtime takes about 0.92×, with 21 tests passing including a no-sync regression test. Separately, pinning to efficiency cores made every engine about 1.7× slower than pinning to performance cores. With server and client pinned to performance cores, three trials on the same 24-request trace gave goodput 0.70–0.95 req/s for V0, 1.05–1.10 for V1 single and 1.00–1.20 for V1 batch. Still exploratory: 24 requests per trial and 6 of 9 runs missed the 5 ms send-lag target. See `docs/learning/phase-03.md` section 9.
- Open limits: the 1.2 req/s trace is too light to separate V1 batch from V1 single; V1 batch TPOT P95 is unstable (31–109 ms) for an uninvestigated reason; mixed-length requests are processed in separate numerical cohorts; the 512 MiB cap is a guard rather than a profiled pool. vLLM remains blocked by Windows/WSL2. Continuous batching, abort lifecycle, and owned paged allocation belong to later phases.
- Proposed for the user's decision, not adopted: pin benchmark server and client to performance cores, keep a GPU clock trace with every run, interleave engines within each trial, and add a higher offered rate. These would change `docs/benchmarking.md`.
- Next: Phase 4 continuous batching and stream/abort lifecycle after the user says "continue".
